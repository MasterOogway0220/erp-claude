# src/lib/auth/otp.ts

> Issues a login code to a user's email and verifies it back. The database and
> SMTP half of two-factor login.

## Why this exists

Two-factor authentication was requested for eight named staff logins. The code
is emailed rather than generated by an app because those users already have
company mailboxes and nothing to install.

This file owns the parts that touch the world — Prisma and `nodemailer` — while
`otp-policy.ts` owns the decisions. It re-exports the policy module so callers
need a single import.

## What it does

| Export | Behaviour |
|---|---|
| `issueOtp(email, name)` | Supersedes any live code, stores a new hash, mails it. `false` if inside the cooldown. |
| `verifyOtp(email, code)` | Checks and consumes. Returns the policy's `OtpCheck`. |
| *(re-exports)* | Everything from `./otp-policy`. |

## How it works

### Issuing

1. **Cooldown check.** If a code was created for this address within
   `OTP_RESEND_COOLDOWN_MS` and has not been consumed, return `false` without
   sending. The caller renders "a code was already sent" — this is what stops
   a user hammering *Resend* from filling their inbox.
2. **Supersede live codes.** Any unconsumed code for the address is marked
   consumed *before* the new one is written. Without this, an older mail still
   works, which defeats single-use: a code intercepted an hour ago would remain
   valid as long as the user kept requesting new ones.
3. **Store the hash, never the code.** `bcrypt.hash(code, 10)`. Database read
   access must not yield working login codes.
4. **Send.**

### The rollback on send failure

```ts
try { await mailer().sendMail(...) }
catch (err) { await prisma.emailOtp.delete(...); throw err }
```

This was a bug found in review. The row is written before the mail is sent —
it has to be, the hash must exist to verify against. If the send then throws,
leaving the row behind starts the **cooldown on a code that was never
delivered**. The user's next attempt is refused with "a code was already sent"
for a code nobody could possibly have, and they are stuck for a minute with no
explanation. Deleting the row on failure means the retry works immediately.

The delete is itself `.catch(() => {})` — failing to clean up must not mask the
original send error, which is the one worth propagating.

### Verifying

Queries the newest unconsumed code for the address, runs `otpUsable`, then
compares with `bcrypt.compare`.

On a **wrong** code, `attempts` is incremented and the code stays live. On a
**correct** one, `consumedAt` is stamped immediately. That ordering is what
makes brute force expensive: five wrong guesses inside ten minutes burn the
code, and bcrypt makes each guess slow.

Note `verifyOtp` filters on `consumedAt: null`, so the consumed branch inside
`otpUsable` is unreachable from this path. It is kept because `otpUsable` is a
pure function tested independently, and a future caller might pass a consumed
row.

## Gotchas and constraints

- **`EmailOtp` has no foreign key to `User`.** Codes are keyed on the address
  as typed, so an unknown address behaves identically to a known one and the
  endpoint cannot be used to enumerate accounts.
- **Both callers pass the DB email**, not the user's input. MySQL's default
  collation is case-insensitive, so `findUnique` matches `UCJain@n-pipe.com`
  but returns the canonical `ucjain@n-pipe.com`. Issuing against one form and
  verifying against the other would never match.
- **No cleanup job.** Consumed and expired rows accumulate. Harmless at this
  volume; a periodic delete would be trivial if it ever matters.
- **The mail is plain text plus simple HTML** — no template engine, because a
  six-digit code does not need one and the fewer moving parts in the auth path
  the better.
