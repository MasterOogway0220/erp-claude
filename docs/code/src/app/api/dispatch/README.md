# src/app/api/dispatch/ — dispatch and finance

16 files. Packing, dispatch, invoicing, payments.

See [the API pattern](../README.md) for shared conventions.

## The chain

```
PackingList → DispatchNote → Invoice → PaymentReceipt
                    ↓
            Dispatch dossier (compiled PDF)
```

Plus credit and debit notes, and bank reconciliation.

## The dossier

The single most valuable artefact here. It compiles into one PDF everything the
client needs as proof of what they received: client PO, PO acceptance, MTCs,
inspection reports, TPI certificates, lab reports, length tally, colour-code
compliance, packing list and invoice.

It is assembled from **stored documents**, which is why the upload bug mattered
so much — every one of those attachments was being written to a filesystem
Vercel wipes, so the dossier was compiling from files that no longer existed.

## Invoicing

An Indian tax invoice is statutory: both GSTINs, HSN per line, the tax split
shown separately, amount in words, place of supply.

**Place of supply follows the dispatch address**, not the billing address, and
it decides whether GST splits CGST+SGST or lands as IGST. That is why choosing
the dispatch address early in the flow has a tax consequence.

Domestic and export invoices draw from different number series (`INV`, `EXP`).

The **e-invoice payload** for the GST portal is generated by
`business-logic/e-invoice-generator.ts` — but **nothing submits it**, and no
IRN or QR is stored. Treat that as an unfinished feature.

## Gotchas

- **Dispatch is the last point stock moves** — `RESERVED` → `DISPATCHED`.
- Email routes need SMTP, which is unconfigured in production.
- Tax figures must reconcile exactly; the rounding order in
  `src/lib/calc/po-totals.ts` exists so printed components sum to the printed
  total.
